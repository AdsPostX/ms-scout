<objective>
## Goal
Ship the native `markdown` block to production for Scout body rendering — so responses
render with heading hierarchy, blockquotes, and tables rather than a flat wall of text.

Close four rich_text spec gaps (`rich_text_quote`, `strike` style, `language` on
preformatted, ordered list support) as fallback correctness — these apply when the flag
is off and are the prerequisite to a safe rollback path.

## Purpose
Scout's body text today is hand-parsed from markdown into a custom rich_text tree via
`_text_to_blocks()`. This produces flat, equally-weighted text blocks with no visual
hierarchy — blockquotes look like body copy, code has no language hint, strikethrough
is silently dropped. The result is a wall of text where everything competes equally
for attention.

Slack now ships a native `markdown` block that accepts GFM-formatted text and renders
it with proper heading hierarchy, blockquotes, tables, and inline formatting. Adopting
it means Scout's body text renders with the same visual quality as GitHub and Linear
bot output — without maintaining a custom parser.

The rich_text spec gaps are the fallback path: when the markdown block isn't available
(feature flag off, or Slack API rejects it), `_text_to_blocks()` should still produce
correct sub-elements. Closing those four gaps is a correctness fix regardless of the
markdown block adoption.

## Output
- `_markdown_block(text)` builder function added to `scout_ui_kit.py`
- `SCOUT_MARKDOWN_BLOCKS` env flag wired into `wrap_response()` body path
- `_text_to_blocks()` emits `rich_text_quote` for `>` lines
- `_parse_inline_elements()` handles `~~text~~` → `strike: true`
- `_text_to_blocks()` passes `language` field on fenced code blocks
- `_text_to_blocks()` handles `1. 2. 3.` → `rich_text_list` with `style: ordered`
- Tests extended to cover all new paths
</objective>

## Fallback Correctness (AC-2 through AC-5) — when SCOUT_MARKDOWN_BLOCKS is off

These four fixes apply to `_text_to_blocks()`, the fallback parser used when the markdown
block flag is disabled. They are unconditional correctness fixes — no feature flag.

They matter because: (a) the flag could be disabled for debugging or rollback, (b) some
surface paths may always use rich_text, (c) they're prerequisites to being *confident*
about turning the flag on (a clean fallback means a safe rollback).

None of these produce a visible change to users until they encounter the specific pattern
(blockquotes, strikethrough, language-tagged code, ordered lists) in flag-off mode.

  <name>Task 2: Close four rich_text spec gaps in _text_to_blocks() and _parse_inline_elements()</name>
  <files>scout_ui_kit.py</files>
  <action>
    **Gap 1 — rich_text_quote for blockquotes:**
    In _text_to_blocks(), locate the line-by-line parser state machine. Find where `>` prefixed
    lines are currently handled (if at all — they may fall through to plain text). Add a
    blockquote accumulator state analogous to the preformatted buffer:
    - When a line starts with `> `, strip the prefix, accumulate lines into a quote buffer
    - When the quote block ends (non-`>` line), flush as:
      {"type": "rich_text_quote", "elements": [{"type": "text", "text": buffered_text}]}
    - Insert into the rich_text elements list

    **Gap 2 — strike style in inline parser:**
    In _parse_inline_elements(), extend _INLINE_RE to match `~~text~~`. The regex already
    handles `\*\*text\*\*` (bold) and `\*text\*` / `_text_` (italic) and `` `text` `` (code).
    Add `~~([^~]+)~~` as a named group `strike`. In the match handler, emit:
      {"type": "text", "text": matched_text, "style": {"strike": True}}

    **Gap 3 — language field on fenced code blocks:**
    In _text_to_blocks(), when a ``` fence opening line is detected, extract the language
    hint from the line: `language = line.strip()[3:].strip() or None`. When flushing the
    preformatted block, include "language" only when it's non-None:
      block = {"type": "rich_text_preformatted", "elements": [...]}
      if language:
          block["language"] = language

    **Gap 4 — ordered list support:**
    In _text_to_blocks(), detect ordered list lines with a regex: `^(\d+)\.\s+(.+)$`.
    When detected, accumulate into an ordered list buffer (similar to bullet list handling).
    Flush as:
      {"type": "rich_text_list", "style": "ordered", "indent": 0, "elements": [
          {"type": "rich_text_section", "elements": [{"type": "text", "text": item_text}]},
          ...
      ]}
    The number prefix (1., 2., 3.) must NOT appear in the output text.

    Avoid: touching the pipe table handler, the bullet list handler, or any other existing
    state machine paths. These are additive changes to new line patterns only. Do not
    refactor the outer _text_to_blocks() function structure — gap fixes only.
  </action>
  <verify>
    python3 -c "

    print('PASS: Gap 1 — rich_text_quote')

    # Gap 2: strike
    blocks = _text_to_blocks('~~strikethrough~~')
    rt = blocks[0]
    all_elements = [e for el in rt['elements'] for e in el.get('elements', [])]
    assert any(e.get('style', {}).get('strike') for e in all_elements), 'No strike style'
    print('PASS: Gap 2 — strike style')

    # Gap 3: language hint
    blocks = _text_to_blocks('\`\`\`python\ncode\n\`\`\`')
    rt = blocks[0]
    pf = next(el for el in rt['elements'] if el.get('type') == 'rich_text_preformatted')
    assert pf.get('language') == 'python', f'Expected language=python, got {pf}'
    print('PASS: Gap 3 — language field')

    # Gap 4: ordered list
    blocks = _text_to_blocks('1. First\n2. Second\n3. Third')
    rt = blocks[0]
    ol = next(el for el in rt['elements'] if el.get('type') == 'rich_text_list')
    assert ol.get('style') == 'ordered', f'Expected style=ordered, got {ol}'
    items = [e['elements'][0]['text'] for e in ol['elements']]
    assert '1.' not in items[0], f'Number prefix leaked into item: {items}'
    print('PASS: Gap 4 — ordered list')
    "
